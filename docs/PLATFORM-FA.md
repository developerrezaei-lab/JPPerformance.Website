# JP Performance · سامانهٔ مربی و شاگرد، نسخهٔ پایه 0.2

این شاخه بر مبنای `feature/website-fitness-hub` است. برنامهٔ Android در این تغییر توسعه داده نشده است.
این یک نسخهٔ فنی قابل تست است؛ برای پذیرش عمومی دادهٔ واقعی سلامت هنوز آماده نیست.

## ساختار

- `site/`: سایت شرکتی و ابزارهای رایگان قبلی، فونت‌های محلی و لوگوی SVG جدید JP با نماد مغز و دمبل.
- `platform/Api/`: API مستقل ASP.NET Core 10 / EF Core / Identity، مسیر `/api/v1`؛ Vue به کلاس‌های این پروژه وابسته نیست.
- `platform/Portal/`: Vue 3 + Vue Router + Chart.js، مسیر `/portal/`، خروجی استاتیک، بدون CDN.
- SQL Server برای production؛ SQLite فقط برای اجرای محلی و تست. Redis برای کش مشترک کاتالوگ و readiness.
- Nginx سایت، پنل و API را زیر یک دامنه ارائه می‌کند. Caddy فعلی همچنان تنها ورودی 80/443 سرور است. سرویس API و Redis پورت عمومی ندارند.

Razor به این نسخه اضافه نشده: رابط تعاملی با Vue و سرویس مستقل، هدف جداسازی وب/API/موبایل را پوشش می‌دهد. اضافه‌کردن یک میزبان Razor به یک SPA در این مرحله سرویس اضافه‌ای بدون قابلیت جدید ایجاد می‌کند. در صورت نیاز آینده به SSR یا صفحات مدیریتی سرور، می‌توان میزبان Razor مستقلی اضافه کرد؛ قرارداد API ثابت می‌ماند.

## قابلیت‌های پیاده‌شده

1. ثبت‌نام شاگرد، ورود cookie برای وب و bearer/refresh برای کلاینت آینده؛ گذرواژه با Identity هش می‌شود.
2. مدیر اولیه فقط با فرمان یک‌بارهٔ سرور ایجاد می‌شود؛ مدیر می‌تواند دسترسی مربی را تأیید یا حذف کند. ثبت‌نام عمومی امکان انتخاب نقش مربی یا مدیر ندارد.
3. مربی شاگردِ از قبل ثبت‌شده را با ایمیل دعوت می‌کند. دعوت داخل پنل است و ایمیلی ارسال نمی‌شود.
4. فقط پس از پذیرش شاگرد، مربی می‌تواند پیشرفت، دفتر غذا و برنامه‌های او را ببیند. لغو رابطه یا حذف نقش مربی روی درخواست بعدی اعمال می‌شود، حتی اگر قبلاً وارد شده باشد.
5. ثبت وزن و دور کمر، نمودار و جدول مقادیر، ثبت جلسهٔ تمرین و وعدهٔ غذا؛ بازهٔ ۳۰/۹۰/۳۶۶ روز و سقف هزار رکورد جدیدتر برای هر سری.
6. برنامهٔ تمرینی با حرکت/ست/تکرار/استراحت، و الگوی غذایی با غذا/گرم. برنامهٔ تخصیص‌یافته snapshot تغییرناپذیر است؛ اصلاح با برنامهٔ جدید انجام می‌شود.
7. کتابخانهٔ ۱۲ حرکت با تصویر و راهنمای منبع؛ جستجوی ۲۸۵۳ غذای CoFID و محاسبهٔ کالری/پروتئین/کربوهیدرات/چربی سمت سرور. سابقهٔ وعده مقدار محاسبه‌شدهٔ زمان ثبت را حفظ می‌کند.
8. رضایت صریح برای ذخیرهٔ رکورد سلامت، CSRF برای وب، کنترل مالکیت رکوردها، محدودسازی اندازهٔ درخواست، صفحه‌بندی فهرست‌ها، index و محدودیت یکتا برای درخواست‌های تکراری.

ثبت برنامهٔ غذایی در این مرحله «الگوی وعده با وزن مواد» است؛ تقویم چند هفته‌ای، جایگزین غذا، آلرژی، پروندهٔ پزشکی، چت، پرداخت و بازار عمومی مربی پیاده نشده‌اند.

## اجرای سریع Windows / Docker

در پوشهٔ `F:\Apps\AmBusiness\JPPerformance.Website`:

```powershell
git fetch origin
git switch feature/coaching-platform-foundation
git pull --ff-only origin feature/coaching-platform-foundation
.\scripts\Start-Platform.ps1 -Build
```

آدرس: `http://localhost:8093/portal/`؛ سایت همان stack روی `http://localhost:8093/` است. اجرای قبلی سایت روی 8092 می‌تواند هم‌زمان بماند. فقط SQLite محلی است و داده در volume `local-data` می‌ماند؛ `down -v` داده را حذف می‌کند.

برای ایجاد مدیر اولیه، پس از healthy شدن:

```powershell
.\scripts\Initialize-LocalAdmin.ps1
```

گذرواژه را امن و محلی وارد کنید؛ در چت یا گیت قرار ندهید. فرمان فقط وقتی هیچ مدیری وجود ندارد موفق می‌شود؛ حساب عمومی موجود را به مدیر ارتقا نمی‌دهد. ابتدا با مدیر وارد شوید و از «Member access» مربی را تأیید کنید. برای بازگشت به شاگرد یا مربی خارج شوید و با حساب او وارد شوید.

سناریوی تست: حساب شاگرد و مربی را بسازید؛ مدیر، مربی را تأیید کند؛ مربی شاگرد را دعوت کند؛ شاگرد دعوت را بپذیرد؛ مربی برنامه تعیین کند؛ شاگرد اندازه‌گیری/وعده/تمرین ثبت کند؛ شاگرد دسترسی مربی را لغو کند و عدم مشاهدهٔ اطلاعات توسط مربی را بررسی کنید. از دادهٔ ساختگی استفاده کنید.

## آماده‌سازی سرور مشترک؛ اجرای کورکورانه ممنوع

این شاخه دیگر تنها یک سایت استاتیک نیست. فرمان قبلی `deploy/deploy.sh` پنل را راه‌اندازی نمی‌کند. قبل از فعال‌سازی overlay، نسخهٔ فعلی `/opt/jpperformance` و تنظیمات Caddy/Nginx را نگه دارید و از پایگاه داده پشتیبان بگیرید. Caddy فعلی نیاز به تغییر مسیر دامنه ندارد.

اطلاعات موردنیاز از میزبان، بدون نمایش رمزها:

```bash
docker inspect kpdc-sql-1 --format '{{json .NetworkSettings.Networks}}'
docker stats --no-stream
free -h
df -h /opt
```

در SQL Server فعلی **دیتابیس مجزای JPPerformance و login مجزا** بسازید. از دیتابیس سایت KPDC یا رمز sa در تنظیمات این سامانه استفاده نکنید. نام شبکهٔ خصوصی SQL را از خروجی inspect بردارید؛ API فقط به همان شبکه و شبکهٔ داخلی خودش متصل می‌شود. کاربر runtime فقط دسترسی خواندن/نوشتن همین دیتابیس را دارد؛ migration با حساب مجزای دارای DDL در سرویس موقت jp-migrate اجرا می‌شود. رمز migration به سرویس runtime داده نمی‌شود.

```bash
cd /opt/jpperformance
cp .env.platform.example .env.platform
chmod 600 .env.platform
nano .env.platform
```

در `.env.platform`، `JP_SQL_NETWORK` و connection string اختصاصی را تنظیم کنید. TLS و گواهی SQL باید معتبر باشند؛ مقدار نمونه `TrustServerCertificate=False` است. اتصال SQL با گواهی فعلی سرور بررسی نشده است. اگر رمز دارای `$` است، در env فایل مطابق قواعد Compose quote کنید و خروجی config کامل را در چت ارسال نکنید. فقط `config --quiet` برای اعتبارسنجی استفاده کنید.

پس از تکمیل SQL/network/secrets و تأیید منابع سرور، اجرای دستی:

```bash
bash deploy/deploy-platform.sh
```

اسکریپت imageها را می‌سازد، Redis را بالا می‌آورد، migration را یک بار اجرا می‌کند و سپس پنل/API را فعال می‌کند. سایت موجود از bind mount فعلی خوانده می‌شود؛ Vue داخل image مجزا در `/opt/portal` است. هیچ پورت عمومی جدیدی ایجاد نمی‌شود. روی سرور مشترک ۴GB، build هم‌زمان Vue/.NET و سایر پروژه‌ها ممکن است حافظه کم بیاورد؛ بهتر است image در ماشین build ساخته و منتقل شود یا منابع build جدا باشند.

ایجاد مدیر در سرور پس از migration:

```bash
cd /opt/jpperformance
read -rp 'New admin email: ' Bootstrap__Email
read -rsp 'New admin password: ' Bootstrap__Password
printf '\n'
export Bootstrap__Email Bootstrap__Password
docker compose --env-file .env.platform -f compose.yml -f compose.platform.yml run --rm --no-deps -e Bootstrap__Email -e Bootstrap__Password jp-api --bootstrap-admin
unset Bootstrap__Password Bootstrap__Email
```

ثبت‌نام ورزشکار در فایل انتشار با `JP_ALLOW_PUBLIC_REGISTRATION` کنترل می‌شود و پیش‌فرض آن `true` است. برای توقف موقت ثبت‌نام، آن را در `.env.platform` برابر `false` قرار دهید و سرویس API را بازسازی کنید. مقدار به `Membership__AllowPublicRegistration` منتقل می‌شود؛ ساخت حساب، هیچ نقش مربی، سرپرست یا ادمین نمی‌دهد.

برای rollback فوری وب، با همان فایل‌های Compose، نسخهٔ قبلی شاخه و config را بازیابی و سرویس web را با image استاتیک قبلی recreate کنید. داده/volumeها را حذف نکنید. migration فعلی تنها اولیه است؛ rollback کد، rollback خودکار schema نیست.

## ظرفیت ۵۰ هزار کاربر ماهانه

۵۰ هزار کاربر ماهانه معادل ۵۰ هزار اتصال هم‌زمان نیست. نمونهٔ فرض محاسبه: ۲۰ مراجعه در ماه × ۳۰ درخواست API برای هر کاربر = ۳۰ میلیون درخواست در ماه، حدود ۱۱٫۶ درخواست در ثانیه به‌طور متوسط؛ اوج ده‌برابری حدود ۱۱۶ درخواست در ثانیه. این **سناریوی فرضی** است و اندازه‌گیری ترافیک واقعی نیست.

API بدون state نشست داخل process طراحی شده، داده در SQL و کش کاتالوگ در Redis است؛ درخواست‌ها async و فهرست‌ها محدود و صفحه‌بندی‌شده‌اند. کلیدهای Data Protection در volume پایدارند؛ برای چند replica روی میزبان‌های مختلف باید key ring مشترک و محافظت‌شده فراهم شود. image این نسخه، SQL مشترک و Redis یک میزبان، HA محسوب نمی‌شوند.

`load-platform.k6.js` برای staging با حساب‌های ساختگی و بار ۱۰→۵۰→۱۰۰ VU آماده است. هر VU در حلقه یک progress request و یک ثانیه مکث دارد؛ هدف اولیه p95 زیر ۵۰۰ms و خطا زیر ۱٪ است. **این تست هنوز اجرا نشده است**. برای ارزیابی واقعی، دیتابیس با حجم نمایندهٔ ۵۰ هزار کاربر و تاریخچهٔ چند ماه، ثبت/خواندن هم‌زمان، ورود، کش سرد، قطع Redis و SQL، و حافظه/CPU سرور مشترک را بررسی کنید؛ فقط یک دیتابیس کوچک یا endpoint سلامت کافی نیست.

محدودکنندهٔ فعلی API به کاربر/connection IP وابسته است. reverse proxy در این نسخه عمداً X-Forwarded-For نامطمئن را trust نمی‌کند؛ ترافیک ناشناس پشت Nginx در یک bucket می‌افتد (۱۲۰ درخواست/دقیقه). پیش از ترافیک عمومی زیاد، زنجیرهٔ پراکسی‌های مورداعتماد Caddy/Nginx/Cloudflare و محدودسازی IP واقعی را با تنظیم صریح trusted proxies تکمیل کنید. صرفاً اعتماد به هر هدر IP راه‌حل نیست. این مورد مانع اعلام ظرفیت production این نسخه است.

## استقرار روی میزبان فعلی · ۹ نوامبر ۲۰۲۶

اطلاعات ارسالی میزبان: SQL با نام `kpdc-sql-1` در شبکهٔ خصوصی `kpdc_database`، RAM کل ۳٫۷GiB، MemAvailable حدود ۱٫۶GiB و بدون Swap. این شواهد برای شروع یک آزمایش محدود است، نه تأیید ظرفیت ۵۰ هزار کاربر ماهانه.

اسکریپت جدید `prepare-platform.py` جایگزین ساخت دستی حساب‌های SQL است. Python 3 و Docker روی میزبان لازم‌اند. این اسکریپت تنها دیتابیس **جدید** JPPerformance را آماده می‌کند؛ دیتابیس موجود بدون علامت اختصاصی یا login با رمز متفاوت را تغییر نمی‌دهد و با خطا متوقف می‌شود. رمز sa از environment داخل کانتینر SQL خوانده می‌شود و به فایل میزبان یا خروجی کپی نمی‌شود. اگر رمز فعلی SQL با environment کانتینر تطبیق نداشته باشد، اسکریپت خطا می‌دهد و آن را reset نمی‌کند.

رمزهای تصادفی دو حساب `jpperformance_app` و `jpperformance_migrate` در `.secrets/platform-sql.json` با مجوز ۶۰۰ (پوشه ۷۰۰) ذخیره می‌شوند؛ سپس `.env.platform` خصوصی ساخته می‌شود. `.secrets/` و فایل env از Git و build context حذف شده‌اند. فایل خصوصی موجود overwrite نمی‌شود. خطای SQL قبل از ساخت env، رمزهای JP تولیدشده را برای retry نگه می‌دارد؛ فایل secrets را پس از یک تلاش ناموفق پاک نکنید.

فرمان آماده‌سازی در حالت پیش‌فرض `TrustServerCertificate=False` دارد و برای SQL با گواهی معتبر است. گزینهٔ `--trust-local-sql-certificate` را فقط برای SQL همین میزبان در شبکهٔ خصوصی Docker به‌کار ببرید: اتصال همچنان `Encrypt=True` است ولی اعتبار گواهی محلی بررسی نمی‌شود. این گزینه HTTPS سایت و Caddy/Cloudflare را تغییر نمی‌دهد. برای استقرار عمومی با دادهٔ واقعی، گواهی معتبر یا پین‌شده و تنظیم اعتبارسنجی مناسب را برقرار کنید.

شروع روی همین میزبان با SQL دارای گواهی محلی:

```bash
(
set -e
cd /opt/jpperformance
git fetch origin
git switch feature/coaching-platform-foundation
git pull --ff-only origin feature/coaching-platform-foundation
python3 deploy/prepare-platform.py --trust-local-sql-certificate
bash deploy/deploy-platform.sh
)
```

اگر `.env.platform` از قبل وجود دارد، prepare متوقف می‌شود تا تنظیمات قبلی overwrite نشوند. متن خطا را بررسی کنید؛ فایل خصوصی را بدون بررسی حذف نکنید. اسکریپت build حداقل ۶GiB فضای خالی Docker و ۷۶۸MiB حافظهٔ در دسترس را بررسی می‌کند، هیچ image/volume را prune نمی‌کند و ساخت API و وب را ترتیبی انجام می‌دهد. این کنترل‌ها احتمال فشار حافظه را کاهش می‌دهند و تضمین جلوگیری از OOM نیستند.

محدودیت سرویس‌های جدید: API برابر ۳۸۴MiB، Redis برابر ۹۶MiB با cache حداکثر ۴۸MiB، وب برابر ۹۶MiB. تنظیمات و محدودیت‌های SQL، KPDC، VPN و Caddy دست‌نخورده‌اند. سرویس migration هم موقتاً تا ۳۸۴MiB محدود است. با رشد SQL یا ترافیک، دوباره MemAvailable، OOM و latency را اندازه بگیرید.

پس از موفقیت deploy و نمایش healthy برای API/web، مدیر اولیه را ایجاد کنید:

```bash
cd /opt/jpperformance
bash deploy/initialize-server-admin.sh
```

ایمیل مدیر و رمز را فقط در ترمینال خودتان وارد کنید؛ لازم نیست مقصد ایمیل Cloudflare با ایمیل ورود مدیر یکی باشد. سپس `/login/` و گزینهٔ Administrator را باز کنید. ابزار ساخت مدیر فقط یک بار و برای ایمیل جدید موفق می‌شود. تأیید ایمیل ورودی با Email Routing، SMTP ارسال یا بازیابی رمز برنامه را فعال نمی‌کند. ثبت‌نام عمومی production هنوز پیش‌فرض بسته است؛ ابتدا مدیر و استقرار را با دادهٔ ساختگی بررسی کنید.

تأیید محلی تغییرات استقرار: ۷ تست با runner شبیه‌سازی‌شده برای حفاظت فایل‌ها، عدم overwrite، نبود رمز در argv، retry بدون تغییر رمز، حذف رمز از خطا و گزینهٔ TLS؛ syntax پایتون/Bash و YAML نیز بررسی شده‌اند. این‌ها اجرای واقعی SQL Server/Docker را تأیید نمی‌کنند. نخستین اجرای واقعی روی میزبان شما باید از خروجی prepare، migration و healthcheck بررسی شود.


## ورود مشترک و سرپرست مربیان · ۹ نوامبر ۲۰۲۶

صفحهٔ `/login/` اکنون فقط یک فرم ایمیل/رمز دارد. انتخاب نقش و دکمه‌های سه‌گانه حذف شده‌اند. فرم با API واقعی ورود کار می‌کند و پس از موفقیت به `/portal/` می‌رود؛ خطای اتصال یا رمز اشتباه در همان فرم نشان داده می‌شود و دکمه برای تلاش دوباره فعال می‌ماند. نقش، ورودی قابل انتخاب یا پارامتر ورود نیست. داشبورد و منو پس از دریافت `/api/v1/me` و بر اساس دسترسی واقعی تعیین می‌شوند. چند نقش می‌توانند هم‌زمان به یک حساب داده شوند؛ اولویت صفحهٔ اصلی: مدیر، سرپرست، مربی، ورزشکار. ابزار شخصی و پیشرفت از My progress در دسترس است.

- Athlete: برنامه‌ها و سوابق شخصی و ارتباط رضایت‌محور با مربی.
- Coach: دسترسی قبلی به ورزشکارانِ مرتبط با رضایت فعال.
- Supervisor: فهرست مربیان تخصیص‌یافته و تعداد ورزشکاران فعال آنان، بدون دسترسی خودکار به پروندهٔ سلامت، وعده‌ها یا برنامه‌های ورزشکاران.
- Admin: تأیید/حذف نقش Coach و Supervisor و تخصیص مربیان به سرپرست؛ مدیریت حساب‌های مدیر همچنان خصوصی است.

سرپرست خودش نقش یا مربی به خود تخصیص نمی‌دهد؛ این کار فقط با مدیر است. حذف نقش سرپرست، تخصیص‌های او را حذف می‌کند. نقش یا تیم جدید به حسابی که بعداً دوباره تأیید می‌شود خودکار برنمی‌گردد. تمام مجوزهای حساس در API و از دیتابیس جاری بررسی می‌شوند؛ مخفی‌کردن منو به تنهایی کنترل دسترسی نیست.

### اصلاح HTTPS پشت پراکسی

در بررسی مستقیم با curl، endpoint `/api/v1/auth/csrf` پاسخ HTTP 500 از برنامه می‌داد. در تنظیم قبلی، Nginx مقدار HTTPS ورودی Caddy را با scheme داخلی HTTP جایگزین می‌کرد و API نیز scheme را بازسازی نمی‌کرد. این حالت با `Cookie.SecurePolicy=Always` با تولید توکن ضدجعل سازگار نیست.

Nginx اکنون پروتکل اصلی Caddy را تنها با مقادیر مجاز http/https ارسال می‌کند. API فقط وقتی IP اتصال با آدرس DNS سرویس تنظیم‌شدهٔ `Proxy__TrustedProxyHost=web` تطبیق دارد scheme را می‌پذیرد. شناسایی DNS هنگام درخواست انجام و کوتاه‌مدت کش می‌شود تا startup/readiness API به شروع web وابسته نشود؛ IP جدید در rolling deployment نیز بازخوانی می‌شود. هدر از اتصال نامطمئن پذیرفته نمی‌شود و X-Forwarded-For هنوز trust نشده است. کوکی‌های production همچنان Secure باقی مانده‌اند؛ کاهش امنیت کوکی راه‌حل استفاده‌شده نیست.

migration جدید `CoachSupervision` جدول تخصیص را به SQL اضافه می‌کند؛ migration اولیه حذف یا بازنویسی نشده است. اسکریپت `deploy-platform.sh` هر دو migration را اجرا می‌کند. برای SQLite توسعه، جدول تخصیص در صورت نبودن بدون حذف رکوردهای قدیمی ساخته می‌شود.

برای به‌روزرسانی استقرار موجود، فایل env و رمزها را مجدداً نسازید:

```bash
(
set -e
cd /opt/jpperformance
git fetch origin
git switch feature/coaching-platform-foundation
git pull --ff-only origin feature/coaching-platform-foundation
bash deploy/deploy-platform.sh
)
```

بعد از deploy، `/login/` را با Ctrl+F5 باز کنید. برای عیب‌یابی:

```bash
cd /opt/jpperformance
docker compose --env-file .env.platform -f compose.yml -f compose.platform.yml ps -a
docker compose --env-file .env.platform -f compose.yml -f compose.platform.yml logs --no-color --tail=80 jp-api web
curl -sS -o /dev/null -w 'Sign-in API HTTP %{http_code}\n' https://jpperformance.co.uk/api/v1/auth/csrf
```

از فرستادن env، فایل secrets، cookie یا رمزها خودداری کنید. تست HTTPS محلی شامل صدور CSRF با کوکی Secure، ثبت‌نام/ورود cookie پشت gateway مورداعتماد، رد اتصال مستقیم HTTP و هدر جعلی و مبهم است. این تست‌ها جای اجرای واقعی imageها و تأیید نهایی روی سرور را نمی‌گیرند. ثبت‌نام عمومی production و بازیابی رمز ایمیلی همچنان طبق محدودیت نسخهٔ پایه‌اند.


## تجربهٔ حساب: منوی آگاه از نشست و ثبت‌نام مستقل

منوی عمومی اکنون با GET `/api/v1/me` و cookie فعلی از سرور به‌روز می‌شود. پس از ورود، Sign in و Create account جای خود را به نام کاربر و منوی My dashboard / My progress / Sign out می‌دهند؛ لینک پایین صفحه نیز به My dashboard تبدیل می‌شود. نام کاربر فقط با textContent نوشته می‌شود. هیچ وضعیت احراز هویت یا نامی در localStorage ذخیره نشده است.

در برگشت از تاریخچهٔ مرورگر، فعال‌شدن مجدد تب و اعلان ورود/خروج تب دیگر، نشست دوباره بررسی می‌شود. BroadcastChannel فقط پیام تغییر نشست را منتقل می‌کند، نه نام، cookie یا token. پاسخ دیررس قبلی نمی‌تواند نشست جدیدتر را بازنویسی کند. خطای موقت شبکه هم یک حساب شناخته‌شده را به‌اشتباه خارج‌شده نشان نمی‌دهد.

آدرس ثبت‌نام `/register/` است و لینک آن در منوی عمومی، تب بالای ورود و متن پایین فرم واضح است. ورود و ثبت‌نام هر دو کارت فشرده با فونت خوانا دارند؛ عنوان تبلیغاتی بزرگ حذف شده است. وقتی کاربر از قبل وارد شده باشد، صفحهٔ ورود/ثبت‌نام به‌جای فرم، وضعیت حساب و لینک داشبورد را نشان می‌دهد. محدودیت ثبت‌نام عمومی production تغییر نکرده است؛ اگر بسته باشد، فرم پیام روشن نشان می‌دهد و حسابی ساخته نمی‌شود.

پرتال فقط بعد از شناسایی حساب معتبر منوی کناری را رندر می‌کند. کاربر مهمان به `/login/` منتقل می‌شود؛ لینک قدیمی `/portal/?register=1` و مسیر `/portal/register` به `/register/` می‌روند. مسیرهای محافظت‌شده پس از ورود با allowlist باز می‌شوند؛ next نمی‌تواند کاربر را به دامنهٔ دیگر بفرستد. خطای سرویس به‌صورت کارت کوچک و بدون منوی عضو نمایش داده می‌شود.

تست‌های جدید: خواندن نشست، خروج با CSRF، بازگشت امن، ثبت‌نام/ورود/ذخیرهٔ پروفایل، رد ثبت‌نام بسته، و همگام‌سازی منوی عمومی شامل عقب/جلو مرورگر و پاسخ دیررس. تست API backend مربوط به نسخهٔ قبل است؛ در این تغییر، endpointها و سیاست‌های backend عوض نشده‌اند. ساخت Vue و بررسی تصویری فرم‌های عمومی و حالت مهمان انجام می‌شود.

### خوانایی و مسیرهای حساب — ۲۰۲۶/۱۱/۰۹

- مسیر رسمی ثبت‌نام `/register/` است. Nginx درخواست‌های قدیمی `/portal/?register=1` و `/portal/register` را پیش از بارگذاری پنل به آن هدایت می‌کند؛ `/portal/login` نیز به `/login/` می‌رود.
- صفحات ورود و ثبت‌نام با `Cache-Control: no-store` و دارایی‌های عمومی با نسخه `20261109.5` ارائه می‌شوند. اگر در Cloudflare برای HTML قانون کش سفارشی دارید، باید همان دو مسیر را از کش مستثنی کنید.
- متن معمولی ۱۶، کنترل‌ها و برچسب‌ها ۱۴ و توضیحات فرعی حداقل ۱۳ پیکسل هستند. نوشته کوچک برند و جزئیات تصویر نمایشی تلفن استثنا هستند. فایل `site/assets/readability.css` باید پس از سایر CSSهای عمومی بارگذاری شود.
- بررسی مرورگر روی ۱۴ صفحه عمومی و پنل‌های ورزشکار، تغذیه، حرکات، مربی، مدیریت و سرپرستی با داده ساختگی انجام شد. ثبت‌نام، ابزارها و پنل در عرض موبایل نیز بررسی شدند؛ داده آزمایشی ذخیره نشد.
- اعتبارسنجی این تغییر: ساخت Vue، ۵۶ بررسی ابزارها، ۳۵ بررسی ورود و مجوزهای ناوبری و ۱۲ بررسی وضعیت حساب در منوی عمومی موفق بود. پیکربندی Nginx باید در محیط Docker مقصد نیز اعتبارسنجی شود.
- انتشار با شاخه `feature/coaching-platform-foundation` و همان `bash deploy/deploy-platform.sh` انجام می‌شود. فایل‌های محیط و رمزهای فعلی را نگه دارید و آماده‌سازی اولیه را دوباره اجرا نکنید.

### فعال‌سازی ثبت‌نام و تصاویر — ۲۰۲۶/۱۱/۰۹

پیام «Account registration is not open yet» از گیت تنظیمات production می‌آمد؛ فایل compose متغیر عضویت را به API نمی‌داد. اکنون `Membership__AllowPublicRegistration` از `JP_ALLOW_PUBLIC_REGISTRATION` با پیش‌فرض true گرفته می‌شود. مقدار صریح false در `.env.platform` همچنان ثبت‌نام را متوقف می‌کند. برای اعمال تنظیم باید `deploy/deploy-platform.sh` اجرا شود؛ reload کردن مرورگر یا Nginx به‌تنهایی کافی نیست. این تغییر هیچ نقشی به ثبت‌نام‌کننده نمی‌دهد.

چهار تصویر تولیدی ارسالی مالک سایت به WebP در دو اندازه تبدیل شدند و در صفحه اصلی، کتابخانه حرکات و صفحات برنامه غذایی/تمرینی استفاده شدند. تصاویر مکمل هستند و نمودار آموزشی حرکات را جایگزین نمی‌کنند. جزئیات منبع در `site/assets/images/README.md` آمده است.

اعتبارسنجی: ساخت Vue و ۱۸۲ بررسی (۵۶ ابزارها، ۳۵ ورود مشترک، ۱۲ منوی حساب، ۶۷ HTTP/API و ۱۲ پراکسی/کوکی) موفق بود. تست API روی SQLite موقت با داده ساختگی اجرا شد؛ ثبت‌نام SQL Server روی سرور اصلی هنوز نیاز به تأیید پس از انتشار دارد. تصویرها و نبود اسکرول افقی در نمای موبایل بررسی شدند.
